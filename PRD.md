# Product Requirements Document (PRD)
## Codename: Magma 2.0 (Universal Zero-Day Query Engine)

**Document Version:** 2.0.0
**Status:** Advanced Technical Specification
**Primary Technologies:** Joern (UCPG Extractor), Mojo, MLIR, GPU GraphBLAS
**Core Concept:** Interactive, Cross-Language Tensor Query Engine for Subgraph Isomorphism, optimized for Autonomous AI Agents.

---

## 1. Executive Summary

Magma 2.0 elevates the GPU-accelerated Code Property Graph (CPG) concept from a simple taint-tracker to a Turing-complete, interactive vulnerability research database. It ingests code from multiple interconnected languages (e.g., Python microservices interacting with C++ system libraries), normalizes them into a **Universal Code Property Graph (UCPG)**, and loads them into GPU VRAM as dynamic multidimensional tensors.

Unlike traditional tools designed for human researchers, Magma is architected to be operated by **Large Language Models (LLMs)** acting as autonomous security agents. The engine compiles highly structured, deterministic queries generated by the LLM into optimized linear algebra operations (GraphBLAS) written in Mojo. This allows for instantaneous, interactive hunting of complex vulnerabilities (UAF, TOCTOU, Race Conditions, Memory Corruptions) across millions of lines of code without predefined rules.

## 2. Advanced System Architecture

To support interactive querying and complex bug classes, the architecture is built on four pillars:

### Pillar 1: The Universal CPG (UCPG) Aggregator
* **Concept:** Standard Joern creates language-specific ASTs. Magma implements a homogenization layer. If a Java API calls a C++ JNI library, the aggregator connects the data-flow edge *across* the language barrier.
* **Output:** A massive, unified graph where cross-file and cross-language boundaries are resolved into direct mathematical edges.

### Pillar 2: The GraphBLAS Query Compiler (The Translator)
* **Concept:** AI Agents generate structured payloads (JSON/YAML) defining the topological topology of a vulnerability.
* **Mechanism:** Magma features a compiler built in Python/Mojo that parses the AI's deterministic query and translates it into an Execution Plan consisting of Matrix Multiplications, Hadamard products (element-wise), and Boolean Masking.

### Pillar 3: Tensor-Based Subgraph Isomorphism Engine
* **Concept:** Finding complex 0-days is mathematically equivalent to the "Subgraph Isomorphism" problem (finding a small, specific graph pattern inside a massive graph).
* **Mechanism:** The GPU uses dense and sparse matrix algebra to search for specific geometric topologies (e.g., a branching path where one thread writes and another reads without a synchronization lock node).

### Pillar 4: Value-Set Analysis (VSA) Matrix
* **Concept:** Tracking not just *where* data flows, but *what* the data is. Instead of boolean matrices (0 or 1), edges contain integer ranges or buffer size constraints to mathematically prove if an array index can exceed its buffer size.

## 3. Vulnerability Class Implementations (The "How")

Magma solves advanced vulnerability classes by modeling them as specific graph topologies.

### 3.1. Temporal Memory Safety (Use-After-Free / Double Free)
* **Graph Pattern:** Node A (`malloc/new`) $\rightarrow$ Node B (`free/delete`) $\rightarrow$ Node C (pointer dereference).
* **Matrix Logic:** The engine searches for a path from a `free` node to a `dereference` node where the pointer ID matches, **AND** mathematically subtracts any paths that contain an intervening reallocation or nullification node (`ptr = NULL`).

### 3.2. Concurrency & Race Conditions (TOCTOU)
* **Graph Pattern:** Two parallel execution flows (CFG threads) intersecting at a shared data node (PDG).
* **Matrix Logic:** We create a 3D Tensor where the Z-axis represents concurrent thread execution. A TOCTOU is detected by querying the tensor for a topology where Thread 1 executes a "Check" node (e.g., `if(access(file))`), Thread 2 executes a "Modify" node on the same file, and Thread 1 subsequently executes a "Use" node (e.g., `fopen(file)`).

### 3.3. Memory Corruption (Buffer Overflows)
* **Graph Pattern:** A source node (user input) flowing into a memory allocation node (defining size) and subsequently into a memory copy sink (e.g., `strcpy`, `memcpy`).
* **Matrix Logic:** Using the VSA matrices, the GPU multiplies the "Input Length Constraints" against the "Buffer Size Constraints" along the graph path. If the mathematical maximum of the input vector is strictly greater than the allocation vector at the sink node, it flags a guaranteed overflow.

### 3.4. Advanced Injections & Second-Order Vulnerabilities
* **Graph Pattern:** Data enters the system (Source 1), is stored in a database (Sink 1 / Source 2), and is later retrieved and executed in a vulnerable context (Sink 2).
* **Matrix Logic:** Transitive closure operations on the adjacency matrix over the entire UCPG, effectively calculating the $A^n$ matrix to find multi-hop, asynchronous data flows across different application states.

## 4. LLM-Optimized Magma Query Language (MQL)

Since the primary operator of Magma is an LLM (e.g., Claude Opus), the query language must abandon human-centric "syntactic sugar" (like fluent chained APIs) in favor of **strict, deterministic, and schema-validated data structures**. LLMs hallucinate less and reason better when generating standard formats like JSON.

MQL is designed as a **Declarative JSON Subgraph Specification**. The LLM describes the *shape* of the vulnerability, and the Magma compiler translates this shape into tensor algebra.

**Key Design Principles for AI-Driven MQL:**
1.  **State Independence:** The query must contain its entire context. No chained methods that rely on previous states.
2.  **Explicit Topological Mapping:** Nodes and edges are defined in separate arrays, mirroring Graph theory concepts exactly.
3.  **Matrix-Ready Masking:** Exclusions (like sanitization checks) are defined as `anti_patterns`, which directly translate to Boolean Masking operations in Mojo.

---

## 5. Non-Functional & Hardware Requirements

* **VRAM Pooling:** For massive codebases (e.g., Windows OS or the entire Chrome browser), a single GPU's VRAM won't suffice. The Mojo kernel must support multi-GPU tensor sharding (e.g., via NVIDIA NVLink or Apple M-series Unified Memory up to 192GB).
* **Interactive Latency:** Complex Subgraph Isomorphism queries must return initial results within $2.5$ seconds to enable a truly interactive "hunting" experience, unlike traditional batch-processing SASTs.
* **LLM Integration Engine:** Once a mathematical match is found, the exact subgraph coordinates are sent back to the LLM agent to automatically generate a proof-of-concept (PoC) exploit based on the verified path.

## 6. Annex: MQL Syntax Specification for AI Agents

This section outlines the schema expected from the LLM. The LLM will generate a JSON object containing three main arrays: `nodes` (the target states), `flows` (the topological edges/paths), and `anti_patterns` (the logical subtractions).

### 6.1 Schema Definition

```json
{
  "query_metadata": {
    "vulnerability_class": "Use-After-Free",
    "description": "Find paths where a freed pointer is dereferenced without intervening reallocation or nullification."
  },
  "nodes": [
    {
      "id": "N1",
      "type": "CALL",
      "attributes": { "name": ["free", "vPortFree", "kfree"] }
    },
    {
      "id": "N2",
      "type": "DEREF",
      "attributes": { "is_write": true }
    }
  ],
  "flows": [
    {
      "source": "N1",
      "target": "N2",
      "edge_type": "DATA_DEPENDENCY",
      "max_depth": 100,
      "tracked_variable": "pointer_argument"
    }
  ],
  "anti_patterns": [
    {
      "between": ["N1", "N2"],
      "node": {
        "type": "ASSIGN",
        "attributes": { "value": "NULL" }
      }
    }
  ]
}
```

### 6.2 Translation to Tensor Algebra (Under the Hood)

When the LLM sends the above JSON payload, the Magma Mojo Compiler performs the following mapping:

1.  **Node Identification:** Queries the UCPG dictionary to create a state vector for `N1` ($V_{free}$) and `N2` ($V_{deref}$).
2.  **Path Calculation:** Uses the Data Dependency Adjacency Matrix ($M_{data}$) to calculate reachability up to 100 hops: $\sum_{i=1}^{100} M_{data}^i$.
3.  **Mask Generation:** Creates a mask matrix ($M_{null}$) representing paths that pass through `ASSIGN NULL` nodes.
4.  **Final Isomorphism Equation:** Solves for $Result = (V_{free} \times (\sum M_{data}^i) \times V_{deref}) - M_{null}$.
5.  **Output:** Returns the exact file coordinates where the resultant vector values are non-zero back to the LLM for PoC generation.
